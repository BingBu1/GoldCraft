# Minecraft 发光轮廓

MC 实体轮廓已接入实体导出、原子帧协议和宿主场景回调，并完成生产构建及离线验证。候选包含枪镜、反胃、健康和深度复制等前序修复，尚未部署或实机验收。原生 CS 身体的权威状态、PVS 例外和可靠分发已完成独立候选；客户端注册和真实模型遮罩仍待接入，不能据此认定完整发光效果已完成。

## 实现

`native/client/entity_outline.cpp` 接收当前宿主视角下绘制的实体轮廓遮罩，在独立 RGBA8 目标中完成五邻域边缘检测、横向和纵向半像素线性箱式模糊、原版末尾 blit，再合成到宿主场景。实现独立表达算法；Minecraft 的着色器文件仅由测试工具从本地依赖提取，不发布。

边缘检测和末尾 blit 都保留原版 SRC_ALPHA / ONE_MINUS_SRC_ALPHA 混合。每个中间目标保持 RGBA8 夹限与量化；最后一次 blit 不能简单省略，它会再次改变颜色与 alpha。最终场景 alpha 保持原值，线性目标使用调用方提供的实际宿主 gamma 指数转换轮廓 RGB。原版世界合成的独立 alpha 因子为 ZERO / ONE，Framebuffer 绘制也关闭 alpha 写入。

几何回调使用所提供的真实宿主矩阵与 viewport，输出队伍颜色并保留原版纹理 alpha 裁剪：只丢弃 alpha 恰为零的纹素，1/255 仍进入不透明遮罩。模型染色、受伤覆盖层、顶点 alpha 和光照不改变队伍色。私有遮罩不挂宿主深度，因此不会被墙壁遮挡；保留原版材质剔面，不以 GlowShell 或包围框代替模型。

`HostedOutlineProvider` 在同一次实体渲染调用中读取实际 `hasOutline`、`getAffectedOutline` 和 `getTeamColorValue`，将普通模型与轮廓分到不同批次。每个 consumer 固定该实体的队伍色，避免延迟提交时串色；YSM 包装层先读取真实 delegate 的语义。没有轮廓的层保持原始消费者。渲染层的 Cull 开关位于 Toggleable 父类，使用真实 Mixin accessor 读取，不猜测字段位置。

协议30增加客户端可选能力524288及消息95 `entity_outline_frame`，不改变旧消息66。旧消息仍只接受flags0–7；新消息额外接受8（轮廓）和24（轮廓加剔面），拒绝轮廓与旧深度/混合位混用。模型、轮廓、效果和玩家身份在同一原子帧提交，继续使用原有生命、世界、资源代次、纹理引用、0.5秒新鲜度和消息预算检查。新消息支持TCP及共享内存；没有协商能力的连接不能发送或接收它。旧宿主拒绝未知HELLO时先退回仅反胃能力，再退回旧能力集合，成功连接后的下次重连重新尝试全部能力。

宿主后场景回调先合成实体轮廓，再运行既有全屏效果。普通实体、透明和阴影绘制跳过轮廓批次。断链、旧连接代次、过期生命/帧、无世界/图集、协议不符或上下文失效时不提交绘制；空新帧不重播旧遮罩。缺失纹理或私有合成失败保留宿主颜色。线性场景使用宿主实际gamma cvar。

目标内存上限为 256 MiB，包含 resize 同时保留的新旧资源。稳定尺寸复用三个纹理；实测预热后不增加 C++ 分配或纹理 storage 调用。只有完整图像处理成功才复制回宿主颜色的 viewport 范围，保持宿主深度、模板、其他 MRT 和范围外像素。GL 状态按作用域恢复，禁止跨 context 删除资源。不保留借来的宿主描述符和附件句柄。

## 验证

合成器证据在本地 `build/entity-outline-20261018`，接线证据在 `build/entity-outline-frame-20261018`。生产 GoldCraft 目标与独立 GPU 测试均使用既定 x86 Clang / C++20 / O3 / ThinLTO / AVX2 / 精确浮点构建。

`gpu02/result.json` 固定测试二进制 SHA，原版十份资源逐项 SHA 和管线 JSON 校验。测试直接编译原版 `sobel.vsh`、`blur.vsh`、`blit.vsh` 与对应 fragment shader，在真实 GL core/compat 两种上下文中对照新实现。原版四遍处理在独立 FBO 执行，合成预期再保留宿主 alpha。

两种上下文共 32 组尺寸/存储/颜色空间组合，1,799,505 项像素分量及状态检查通过，包含奇数横竖屏、1×1、子 viewport、彩色/空遮罩、重复帧、RGBA8/HDR、深度/模板/MRT 保持、完整 GL 状态恢复、回调拒绝与 GL 错误、分配失败后的旧代恢复、跨 context 拒绝和无 context 空对象析构。比较容差为 RGBA8 约一阶量化、RGBA16F 0.0011；不是宣称所有浮点输出逐位相同。

## 原生身体权威通道（未接 Studio）

MC 专服用独立可选能力 1048576 和消息 96 `status_glow` 发布 40 字节状态；协议仍为 30，旧隐身消息 89 不变。状态包含世界、递增序号、槽位、连接、出生、当前生命代次、开关与 24 位 RGB。读取真实 `LivingEntity.isGlowing`，同时覆盖药水与命令/Mod 标记；已配对原生形态保留真实玩家的队伍颜色和命令发光，效果仍只有一个所有者，其他玩家不能代供队伍色。

ReGameDLL 只接受已认证专服能力，绑定当前实体表、私有玩家对象、引擎实体 serial、连接、出生、life 和桥接代次；对可重入的存活查询前后重新校验。租约为 350ms，重复/倒序包不能续期。死亡、换人、换图、形态/移动代次改变、断链与时钟倒退均拒绝旧租约。

`AddToFullPack` 仅在真实 PVS 检查失败时允许当前有效发光玩家通过，且接收者必须支持独立 `_gc_outline=1`。隐藏实体、owner、旁观、模型、分组及 localhost 规则继续生效。例外不写入原版一秒 PVS 宽限缓存，发光结束不会因此额外泄露旧位置。没有改动 entvars、碰撞或攻击判定。

可靠 `GCOutline` 消息另加真实 userid/UUID，使用服务端独立分发序号。每次变化/失效立即发送，活动心跳每 150ms；来源每 tick 的序号不会触发全部接收者重发。过期 clear 的序号高于活动帧。新接入者收到下一次活动心跳即可，普通/机器人接收者不发送。`status_glow::Receiver` 已具备严格解析、可靠 roster 身份/存活校验、350ms超时与世界清理，尚未挂接客户端消息与 Renderer，当前运行客户端不会公告该能力。

证据：`build/native-glow-20261018`。生产 mp.dll、GoldCraft.dll 和正式 Core 构建成功；383 项原生检查编译实际处理器、分发函数和生产 AddToFullPack 的准入分支，57 项旧隐身回归通过。首次冻结输入的346项JUnit通过；后续仅两个发布器文件补齐配对队伍色/命令发光，最终正式JAR在无附加Mod及Epic/NightFall两套实际NeoForge运行各通过77项、14条真实TCP消息，包含效果到期、命令标记、永久隐身代理、配对双向交接和身份撤回。ReGameDLL16文件补丁独立回放通过；新Core9个枪镜/深度类与已验联合候选逐字节相同。

这些验证不是完整ReHLDS到真实Studio模型的联机画面。四个产物仅单独冻结，未部署、未替换33项联合候选。下一步接客户端消费和真实Studio姿态/皮肤/纹理alpha遮罩，再与既有MC轮廓统一合成，保留替身抑制及GL状态。
