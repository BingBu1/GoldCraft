## 读取与校验次数

当前 `native/csol/client/resources.cpp::LoadStudio` 在宿主进入 loader 后再次 `ReadResource(model->name)`，以文件系统句柄的实际长度建立安全边界；不能用未验的 header.length 直接替代。`ReadResource` 本身只负责读取与大小限制，不计算 CRC。CRC 的宿主字段适配在 `native/client/precache_client.cpp`，保留原引擎校验；不要把 CRC 耗时与 RLE 安全扫描混称。

| 输入状态 | 当前实际处理 |
|---|---|
| 普通未附加 MDL，无 SEQ | 开头 `ReadSequenceSafety` 和最终 `PreparedSequenceModel::Read` 各判定一次 Absent；没有逐轨 RLE 全扫描 |
| 已有有效安全记录的 MDL | 开头和 Prepared 各完整验证一次真实轨道，共两次；仍会枚举邻接 SEQ 的存在性，但不会 Append |
| 原 MDL 加 SEQ | 开头及 Append 入口只是 Absent 探测；Append 对原动画检查与量化，Prepared 对最终新字节完整验证一次。不能把不同字节世代的检查直接当作重复删掉 |

`SequenceFiles` 每个名称只探测连续后缀，遇首个缺失即停；不是无条件进行 256 次存在性查询。`SequenceOwnerRegistry::CompleteLoad` 只检查实际分配与复制的头/metadata，不再做全轨 RLE 验证；运行采样保护也不做全轨扫描。

`assets.cpp::GetAsset` 有独立的按模型名缓存，首次创建会再读/解码原文件、处理材质与几何。`ClearAssets` 清除此缓存。它可能解释进图首次显示的另一段等待，但本轮没有采样调用次数/耗时，不能称其为已确认瓶颈。

## 服务端诊断审查与验证

父任务新增 `native/engine/model_load_profile.h`，只在 `GOLDCRAFT_MAP_LOAD_TIMING=1` 时记录；范围为 entities / dependencies 两阶段的文件读取、CRC、decode、decode safety、prepared、storage、copy、commit。

初审指出 Phase 析构原先会在 C++ 异常展开时打印，父任务已加 `std::uncaught_exceptions()` 门。本次小测试直接包含生产头，不复制算法：默认/非法开关零时钟、正常聚合、嵌套时长、异常不发布、已捕获异常的尝试计数、嵌套 phase 取消及过时代隔离，共 **32 检查通过**。夹具为 `tests/engine-model-profile`，固定输出 `build/engine-model-profile-tests/result.json`；fake clock/logger，无游戏执行。

诊断解释必须保留：Decode 包含 DecodeSafety 和 SEQ读取/Append，不可直接将所有列相加；file_read 没有统计 Decode 内的 SEQ读取。calls 是已结束作用域的尝试次数，不等于模型成功数。嵌套 Phase 只允许最新正常结束者发布。真正 Host_Error/Sys_Error longjmp 不运行析构；下一 Phase 会重置计数并换代，旧作用域不会混入新报告，夹具没有跨 C++ 对象执行真实 longjmp。
