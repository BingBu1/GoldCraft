# 普通服务器连接与客户端初始化修复

2026-10-10。用户授权诊断沙箱 B 的公网连接和进服后崩溃，连接和游戏操作由用户手动完成。范围为本地启动脚本、GoldCraft 初始化包装和匹配客户端 ABI；原始游戏安装只读，不修改远程服务器，也不绕过服务器 FPS 规则。

公网连接错误和进服崩溃是两个独立缺陷。两处已修复，B 实际进入普通服务器后，用户确认“进服卡了一会现在正常了”。当前结果验证该次连接恢复，尚不等于所有地图、服务器和长时间会话全部通过。进服短暂停顿原因仍待查。

## 证据与结论

| 证据 | 结论 | 路径与处理 |
|---|---|---|
| E01：同一公网 UDP 查询，绑定回环地址得到 WinError 10051；绑定全接口收到 protocol48 A2S_INFO。实际启动参数及 socket 也验证了旧回环绑定 | F01，已验证，高置信度：客户端 `+ip 127.0.0.1` 阻止公网出站 | P01（solve）：`Start-Sandbox → GoldSrc ip → UDP bind`。客户端改为 `0.0.0.0`，本机专服保留回环；端口及本地配对地址不变 |
| E02：真实崩溃为 `c0000005` 执行空地址；匹配 client Initialize 复制 135 个指针，SDK 仅声明 134 个；Director 命令10调用表偏移 `0x218` | F02，已验证，高置信度：SDK 大小的静态表副本截掉最后一个回调 | P02（callflow）：`InitializeClient → 原生 Initialize → HUD_DirectorMessage → 命令10 → 丢失回调`。转发原表指针，仅在同步初始化期间临时替换已知 pEventAPI，并用 RAII 恢复 |
| E03：真实匹配 client 的初始化复制及 Director 分支在修复测试中成功；旧536字节副本对照丢失回调；嵌套、0/1返回和 C++异常均恢复原表 | F03，已验证，高置信度：修复保留未知 ABI 尾部及事件代理寿命 | P03（solve）：不猜完整函数表长度，不把过滤回调替换成不受限命令执行，也不屏蔽 Director 消息 |
| E04：B 修复版实际启动，用户手动进服后确认恢复正常；额外30秒16次状态全部新鲜、普通资源存储、FPS上限99.5、无新访问异常或非法FPS文本 | F04，已观察：这次公网会话未重现空回调崩溃；进服仍有短暂停顿 | P04（solve）：保留诊断至本次会话结束；普通启动默认不开启 qconsole |

E01 的本地原始证据为 `analysis/ordinary-server-network/socket-comparison.json`，SHA256 `f77e49e9987d2b4c9613017c274068baee7df2a0c3221d404c94312c10e4c2bd`。E02 转储为同目录 `director-crash.dmp`，SHA256 `5d9b5e7c718bd92de8ed552d08f95d947f99a21dd95992e97f63ffdd1d6b1ba4`。这些日志和转储含本机及连接身份信息，仅保留本地，不公开分发。

E03 匹配 `client.dll` SHA256 为 `b434b1c09b10b011be6c42e4154955da0c3ca46e95746988ebea1aa316a2a9f2`。测试只对该合法本地副本执行；版本6使真实函数完成540字节复制后返回，不执行完整游戏初始化。随后调用真实 Director 文本分支，用记录 stub 接收原回调。它验证 ABI，不代替版本7初始化和联网实测。

按[构建说明](BUILD.md)准备锁定 SDK、工具链及匹配沙箱客户端后运行：

```powershell
.\tools\Build-Native.ps1
.\.tools\cmake434\cmake\data\bin\ctest.exe --test-dir build/native-clang-x86-Release -R goldcraft_client_initialize --output-on-failure
```

缺少本地匹配客户端时，这两个 CTest 不注册；不能记录为通过。不同 SHA 的客户端会拒绝此固定 ABI 回归，生产修复本身不依赖这些测试 RVA。

## 部署与 FPS 观察

为避免混入并行特效工作，B 的候选来自已经部署的源码基线 `32dd6e8424baefa351392821348db8ed4d070622`，95个构建输入经换行归一后与原构建证据一致，仅加入初始化修复。独立完整 GoldCraft DLL 构建成功，两个实际客户端 CTest 通过。编译保持 x86/C++20/Clang/O3/ThinLTO/AVX2/precise FP；候选 SHA256 为 `68ca361b8c626895b8e2aaf4a5fb097b1e2dd834788cc4936396a21420d548df`。只更新 B 的 GoldCraft.dll，其他插件内容和时间戳保持不变。原安装19572文件的内容、大小和修改时间比较通过。

FPS 日志证明服务器下发的 `fps_max 99.5` 被原生命令过滤拒绝；旧会话后续状态和磁盘配置实际为100。这不能反证用户手动设置时的值。修复启动前，本地配置恢复99.5、fps_override保持0，运行状态确认99.5，cl_filterstuffcmd保持1。此后观察中未出现新的非法FPS提示。

“111”可能与服务器按整数命令毫秒推导有关，但尚无该服务器规则和真实引擎量化路径的完整证据，不记作已确定根因。若99.5时再次出现，应同时采样实际 cvar、帧间隔和原样发送的命令 msec，不伪造 msec 或绕过检查。

时间顺序：先修正回环绑定并获用户连接成功确认；随后诊断捕获真实空回调；真实客户端对照回归和独立审查通过；隔离构建部署；用户先报告“仍卡死或崩溃”，继续观察发现进程和状态更新，用户澄清为“进服卡了一会现在正常了”。保留这一更正，不把初次反馈误记成修复后的第二次访问异常。
