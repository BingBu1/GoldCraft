# ReHLDS 1024 实体快照与客户端接收

日期：2026-10-10。用户最终要求为 **1024**，覆盖此前的 512。该容量限制每个客户端重建的一帧实体集合；已有 4096 绘制队列和动态模型／声音资源表属于不同层。

## 范围

只在工作区合法副本中构建与测试。ReHLDS 是专服引擎；客户端为 SHA-256 `9ba9a2db5e07598fd59afa35507a98c86162e4e15b3835177b78c11842cd2295` 的 GoldSrc 10210。原安装只读，主服、A/B 和 Minecraft 未部署或启动。本阶段不接受图形 B、真实多人或 FPS；不改变已验证的 int32 生命值／护甲通信。

实际执行结果、输入和产物哈希统一保存在本地 `analysis/packet-entities`。最终服务端报告 `native-1791622976232686800.json` 的 56 项检查全部通过，独立服务器退出 0；正式引擎加载检查 `native-1791622947889257100.json` 的 6 项检查通过，正式命令表不包含测试命令。

15 组真实编码涵盖普通 256、错误能力、全量 1024、1025 候选截断、不变／替换／缩减／补满增量、能力降级全量恢复，以及代理、非 IPv4 和事件边界。8 组实际 UDP 捕获覆盖大快照、最大预算、可靠消息及其重发、普通客户端原有超长丢弃行为。实际 `SV_SendClientDatagram` 同包产生 1024 实体和 **257 个真实 BSP 身份**：身份占 3012 字节，应用数据 39722 字节，Netchan 数据 39730 字节，共 29 个 UDP 分片；身份空间少一字节时整组不写。

1024 条身份的编解码另行验证，4096 帧／4194304 次查询没有堆分配。不要将其写成 1024 个真实 BSP 切割目标已通过：在 `cs_assault` 上，512／1024 目标触发既有 3200 万物理事务预算，失败证据保留，预算没有放宽。257 个实际目标足以验证跨越旧 256 上限的同帧身份传输。

最终 29 项 CTest 全通过。`client-receive-final.json` 的 16 项原引擎接收检查及 8 组真实服务端 UDP 捕获通过：执行原 `NET_QueuePacket`、`NET_GetPacket`、`Netchan_Process` 和反加扰，65536 字节完整消息、128 字节可靠内容、同地址重连、来源隔离、48 片单轮交付、96 次工作上限和钩子注册失败回滚均被验证。`client-server-final.json` 分别执行原 x86 位读取、增量／历史解析和实体发布，15 组编码案例及正式发送快照共 16 帧的传输字段逐项匹配；另验证两个事件的 1023 序号和 1024 哨兵。

以上是分层真实代码验证：接收测试映射精确引擎而不执行 DllMain，网络依赖由队列适配；解析测试通过 Unicorn 执行原代码，为外部分配、模型／动画依赖和 CRT 浮点取模提供窄适配。正式发布时原生派生的 `animtime` 按真实分支验证，没有要求它与线上的零值相同。这些检查没有运行完整游戏消息分派、B 画面、预测或多人会话。第一次大消息探针误用另一套反加扰函数的失败日志保留；修正测试编码后，真实服务端捕获及原生 64 KiB 网络处理均通过。

指定 Clang／C++20／O3／ThinLTO／AVX2／精确浮点审计覆盖 12 组、1702 个 C++ 单元和 16 个 x86 产物；10 份源码补丁可重放。最终证据清单为 `analysis/packet-entities/evidence.json`，记录构建、测试输入、产物与源码哈希；GL／Renderer 的 30 个源文件未改。

## Findings

- **F01**：n/a_re，validated，high，E01–E02。原来的 256 硬截断会持续遗漏排序较后的可见实体。1024 扩容同时改变候选选择、快照存储、历史帧和基线边界。能力降级后改发全量快照，避免引用超过普通客户端上限的旧帧。
- **F02**：n/a_re，validated，high，E02–E03。只修改服务端宏不足以完成扩容：原发送缓冲和客户端分片重组会限制较大的快照。新格式仅对协商客户端发送，普通分片继续走原路径；能力声明必须等精确引擎校验与全部接收钩子安装成功。
- **F03**：n/a_re，validated，high，E03。原客户端在不完整分片后退出本轮接收，不能依靠反复手动调用接收函数证明及时交付。扩展路径需要在一次原生收包调用内排空已到达分片，同时限制每轮处理数量，避免无界循环。
- **F04**：n/a_re，validated，high，E01、E04–E05。GCBrush 上限也必须升到 1024，否则超过 256 的快照会丢失整组身份旁路。1024 条身份占 11904 字节；完整空间预检和同序号发布仍保留。动态 BSP 的 Renderer／碰撞消费者是独立后续任务。

## Path

P01，callflow：真实 AddToFullPack → 玩家优先且最多 1024 的有序实体集合 → 全量／增量 packetentities → 同帧 GCBrush → 原事件／ping → Netchan 与既有可靠消息合并 → 1400 字节 UDP 分片（E01、E04，F01–F02、F04）。

P02，callflow：原 NET_GetPacket → 有界 NET_QueuePacket 包装 → NET_GetLong 扩展重组 → 核对当前服务器 IPv4／端口 → 完整 64 KiB 内消息 → 原 net_message 拷贝、Netchan 和实体解析／发布。新连接的原 Netchan_Setup 清除重组状态；普通消息与普通分片保留原处理行为（E02–E03，F02–F03）。

扩展头为 21 字节：原分包标记 -2、31 位序号、保留 packetID 0、GCPK 标记、总长度、分片编号／数量。每片最多 1379 字节负载，一条 65536 字节消息最多 48 片；最多处理 96 次扩展分片后返回。重组不分配逐片堆内存。

## 有限容量与性能边界

1024 是实体数量上限，不是无限消息容量。消息总量上限 65536 字节；服务端快照预算 61520 字节，为既有最大可靠消息和头部留空间。大量字段同时改变、事件或插件额外消息仍可能触发原生溢出处理；不能保证任意 1024 个极端状态都能塞入一包。缺失身份旁路不会授权旧 BSP 切割。

实际高变动状态的全量为 64633 字节、增量为 69255 字节，均超过快照预算。对后者使用真实有界编码器验证溢出标记、缓冲区哨兵不变和原生清空，随后同一客户端的正常 1024 实体快照恢复成功（36659 字节）。没有引入静默截断、自动调低数量或无限重发策略；沿用原生超预算丢弃行为，后续仍需真实场景的网络与帧时间验收。

固定历史存储每个帧槽占 `1024 × 340 = 348160` 字节；64 槽填满约 21.25 MiB／网络客户端，32 个网络客户端约 680 MiB。普通客户端也共用该存储上限；假人不会走发送快照路径。64 KiB 消息的 48 个分片还带有传输头开销，增加容量不会自动提高 FPS 或带宽。

## 复现

先按 [构建说明](BUILD.md) 准备固定依赖和合法游戏副本，在具有控制台输入的终端执行：

```powershell
./tools/Build-Native.ps1 -Server
./tools/Build-ReHLDS.ps1
./tools/Build-Native.ps1 -Server -HeadlessFixture
./tools/Build-ReHLDS.ps1 -TestPacketEntities
python tools/Exercise-PacketEntities.py
python tools/Exercise-PacketEntities.py --production-smoke --engine build/rehlds/Release/swds.dll
```

运行目录只使用独立 `sandbox/packet-entities`。将生成的 `run-*` 目录传给 `Test-PacketEntityClient.py --server-fixture` 和 `goldcraft_packet_client_engine_tests.exe` 的第二个参数，分别验证真实服务端状态解码与真实 UDP 字节在原引擎接收路径中的重组。

正常部署时需同时更新 ReHLDS、GoldCraft.dll 和匹配的 `goldcraft-packet` 元数据。已有实例使用 `Deploy-OptimizedNative.ps1`；新实例初始化也会生成该目录。只替换服务端或缺少精确客户端元数据，不会启用扩展能力。
