# CoF 九枪弹药登记与 870 购买

Remington 870 已在本地专服启用。在沙盒 B 的穷途末路中，选人后取得默认 K3，按 B 打开霰弹枪分类并花 $3000 买到 870。购买备弹后切到小刀再切回，连开两枪将弹仓从 5 发打到 3 发。下一次画面显示弹仓 5 发、备弹从 345 发减到 343 发，确认两发已补回。镜头采样期间检测到玩家输入，因此没有记录到两次补弹的独立动画帧。

## 故障和修改

常用本地服务器还在使用八枪配置。安装包含 870 的九枪配置后，旧 GameDLL 的弹药登记越过 31 个可用槽位，从槽 1 重新写入。隔离服读到槽 1、2、3 分别被 M16、G43、870 的独立弹药名占用。槽 3 原有的 556NatoBox 被覆盖，K3 装备初始化无法取得该弹药槽。

| 证据 | 观察 | 源码与验证 |
| --- | --- | --- |
| 旧隔离服的实际 PDB 和内存读取 | 弹药游标回到 3，前 3 个原生槽被覆盖 | [冷启动回归](../tests/cryoffear-host-cold/run.py)，本地回执 `build/cof-ammo-slots-cold-old-20261118-02/receipt.json` |
| 当前 ReGameDLL 的 AddAmmoNameToAmmoRegistry 及三枪的 ItemInfo 和库存转移调用 | 已登记的同名弹药复用原槽，在冷启动时无须消耗额外槽位 | [武器目录](../native/guest/cof/catalog.hpp)，M16、G43、870 分别使用 556Nato、762Nato、buckshot |
| 新隔离服的实际 PDB 和内存读取 | 登记游标稳定在 31，原生槽 1–5 保持，九把客串武器都已注册 | 同一冷启动回归通过，另有 237 项实际 HTTP 全文哈希。回执 `build/cof-ammo-slots-cold-new-20261118-02/receipt.json` |

同弹种武器现在共享备弹。目录、引擎登记和弹药转移使用同一弹药名。该变更是 GoldSrc 宿主适配。武器查表在编译期确定，射击帧沿用原来的弹药访问路径。

## 构建与实机

Win32 原生 GameDLL 完整链接成功。本地实载 DLL SHA-256 为 `84ea776759a0eb7ec1c91346801d17344c348de699d45e3b49b1c68b9efdf58e`，内存 CodeView 与磁盘 DLL、PDB 匹配。全树扫描检测到一份并发编辑的 Pawn 文件，随后重核 3,196 项其余输入及原生编译读取记录。通用依赖审计另因旧读取日志覆盖不足退出。两项限制及原失败记录保留在本地构建回执。

本地部署更新服务端 DLL、PDB、伤害配置、购买目录和 HUD 目录。初次启动没有继承完整 Windows 环境，恢复启动时地图编号尚未应用。现已用完整环境启动，在本地设定灾变模式 2 和穷途末路编号 98，并根据实际进程创建时间、模块及 PDB 补写启动登记。连接前核对了全部 322 项 HUD 资源。购买目录、人物、资金和武器 HUD 在 B 的实际画面中可见。核验记录为 `build/cof-ammo-slots-local-20261118-01/runtime-recovered.json`。
