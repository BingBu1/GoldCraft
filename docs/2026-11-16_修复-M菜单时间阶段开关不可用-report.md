# M 菜单时间阶段开关不可用

时间阶段条目能在管理员设置中显示，但开启请求被服务端以“功能尚未安装”拒绝。原因是实际阶段消费者已经接线，设置服务的能力列表仍漏掉 `TimeCycle`。随后用户纠正“既然是cvar为什么还要换图后生效”，本次将时间开关和两段时长改为当前地图即时消费。当前未部署或操作游戏界面。

## 依据与源码

本项是用户指定的正午／黄昏／永夜自定义规则和管理接口，不修改 CSOL 原版还原算法。修改前记录在 `analysis/csol-custom-time-admin-20261116/preedit.json`。

| 证据 | 结论 | 对应位置 |
| --- | --- | --- |
| 旧时间描述符已有秒数、开关和 `NextMapSession` 作用域；用户明确要求即时修改 | 这是自定义规则的限制修复，不是推测原CSOL行为 | `native/csol/scenario/custom/settings.cpp` |
| 实际规则的 `Precache`、`UpdateCustomTime` 已使用配置，准备环境／音乐／HUD并推进阶段 | 时间开关已有消费者，不是空开关 | `native/csol/server/scenario/core/game_rules_gate.cpp` |
| 设置服务 `Read` 和 `Edit` 共用 `Available`，其中漏掉 `TimeCycle` | 显示条目后，开启事务仍被拒绝 | `native/csol/server/custom/gameplay_settings.cpp` |
| M 菜单通过 `csol_custom_read/edit` 读取、反转布尔值，保存后复核权限／修订／结果 | 修正后端能力即可复用原权限与持久保存链 | `amxx/scenario/goldcraft_scenario_admin.sma` |

已安装能力列表补入 `TimeCycle`，并在开启前检查当前地图是否已准备阶段资源和引擎光照服务。其余未安装功能继续拒绝开启；实际回归专门保留熟练度和完整疾跑的拒绝用例。保存仍走 userid、修订号、完整 JSON 校验、后台原子替换和主线程发布。

## 当前局如何生效

以下三项在下一次规则帧消费。M菜单保存后永久写入同一个 `addons/goldcraft/config/gameplay.json`；控制台直接修改是临时覆盖，不自动写回文件。

| CVAR | 当前局行为 |
| --- | --- |
| `csol_custom_time_cycle` | `0`结束当前时间周期，并清理阶段HUD、阶段BGM、光照／雾、阶段体力覆盖和客户端随身光；`1`建立新周期，从正午开始，保留当前地图、关卡、人物和物品。 |
| `csol_custom_midday_seconds` | 正午中修改保留已过时间；缩短到已超时则本帧进入黄昏；黄昏／永夜不会倒退。 |
| `csol_custom_dusk_seconds` | 黄昏中修改保留已过时间；缩短到已超时则本帧进入永夜；永夜不被延长的配置拉回黄昏。 |

新周期继续受原有准备／通关／失败状态约束，不借开关重开游戏或复活玩家。普通关卡推进保留同一周期；已提交的重玩才新建周期。原默认180／120秒不变。其他资源、光照数值等仍保留自己的作用域，本次不把所有CVAR宣称为即时。

`CSOL_ReadTimeCycleControls`直接读取注册后的三项CVAR数值，热路径不查字符串表、不读JSON、不分配、不预缓存资源。阶段资源、消息和引擎服务在地图冷准备时验证；缺少可选配套且时间关闭的地图仍可玩，开启请求清楚拒绝，不能在帧内补读资源。单次非法配置保持上一个有效状态并限次提示，纠正后继续应用。

执行链为 `M菜单/控制台 → 原子保存并主线程发布（仅菜单） → CSOL_ReadTimeCycleControls → UpdateCustomTime → ChallengeCycle/PhaseClock → 既有环境/音乐/体力/客户端灯与阶段HUD消费者`。开关与改时长按地图、runtime、关卡和消息修订验证生命周期，回调撤销runtime后不继续发送旧状态。没有更改怪物或BOSS的AI。
