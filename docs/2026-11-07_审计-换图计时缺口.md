## 主要遗漏是 SV_LoadEntities

实际命令入口是 `Host_Changelevel_f`（`host_cmd.cpp:1064`），没有 `SV_ChangeLevel_f`：

```text
PF_IsMapValid_I → SCR_BeginLoadingPlaque / S_StopAllSounds
→ SV_InactivateClients → SV_ServerShutdown
→ SV_SpawnServer [已有 spawn timer]
→ SV_LoadEntities [没有 timer]
→ SV_ActivateServer hookchain
  → SV_ActivateServer_internal [已有 activate timer，内含 dependencies]
```

`SV_LoadEntities`（`sv_main.cpp:6720`）读取可选 `.ent` 或直接使用 BSP entity lump，调用 `ED_LoadFromFile`（`pr_edict.cpp:312`），逐个解析 keyvalue 并调用游戏 DLL 的 `pfnSpawn`。第一项 worldspawn 通过 `CWorld::Spawn → Precache` 安装游戏规则、准备灾变表与资源、购买菜单、普通/扩展武器和角色。**spawn timer 在这些工作开始前已经结束。** 目前 `serverLoadSeconds = spawn + activate` 名称不准确，应称为已计时阶段之和。

差值还包含关服回调、hookchain外围和测量端开销，不能全部称为 `SV_LoadEntities` 实测耗时。但日志提供了直接线索：`L1107039/041/043.log` 的 spawn 分别在 15:23:01/12/22 结束；注册 `CSOChar` 后分别在 03→08、14→18、24→28 有 4–5 秒空档，随后出现 `TempEmit`/`GCNausea` 等注册，再结束约 2.44–2.60 秒 activate。

当前 `CSOL_PrecacheCharacters` 在注册 CSOChar 后读取角色目录及清单，逐项 `GET_FILE_SIZE`，然后逐项预缓存；本地实际 `shader/csol/characters.txt` 有 797 项，其中 180 个 MDL。`COM_FileSize`（`common.cpp:2019`）确为 VFS open→size→close，不读模型正文；随后模型预缓存仍会读/转换模型。这个区间还包括后续扩展武器等工作，不能仅凭两个日志时间将整段归因角色。服务端源码与现运行 mp 的逐 TU 身份不在本轮重新核验范围。

## DLL、日志与文件存在检查

- `changelevel` 不调用 `LoadEntityDLLs`。`Host_Map_f` 只有 `!g_psvs.dll_initialized` 时才调用 `Host_InitializeGameDLL → LoadEntityDLLs`；`ReleaseEntityDlls` 在 Host_Shutdown 全局退出路径。正常同进程换图不能称为反复加载 mp.dll。Metamod/AMXX 自身地图回调是否重载插件需单独计时。
- `SV_ServerShutdown`（`sv_main.cpp:6436`）在 spawn 外，调用 Steam level notification 与 `pfnServerDeactivate`；这段确实漏测，不能据源码宣称没有成本。
- `Log_Open`、`Log_PrintServerVars`、`Host_ClearMemory`、BSP加载、CRC/PAS均在已有 spawn timer 内。三轮 spawn 0.153–0.373 秒，因此这些不能解释额外约6秒。
- `PF_IsMapValid_I` 在 changelevel 前置阶段，只查一次 `maps/<name>.bsp` 的 `FS_FileExists`；它未计时，但不等于全资源扫描。activation内的地图资源存在检查已经计入 activate。角色/武器的文件检查落在遗漏的实体准备阶段，应按具体消费者分开量。
- `Log_Printf` 将 timestamp 在写入前取得；4–5 秒日志间隔不是单纯文件缓冲造成的假时间差。启用 Metamod debug 的日志量和回调开销仍应记录为测试配置，不能凭此假定全部卡顿来自打印。

## 测量工具边界及最小补点

`Measure-MapTransition.py` 的 observed 从发 changelevel 前到新日志+后续status成功；`GoldSrc-Command.py` 每次收包有 0.25 秒静默窗口，首次响应/挑战有3秒超时，测量器另有0.1秒轮询。本地共1148个 L 日志，每轮反复glob/stat也计入 observed。`log on` 刷新与 `gc_cache_stats` 在 observed截止后，不解释该次差值。RCON通过引擎主线程执行，后续status能证明同步调用返回；但收包/文件枚举开销必须和服务器timer分开。

建议第一轮只加4个聚合timer，不逐文件刷日志：

1. `Host_Changelevel_f` 完整入口到正常返回（`changelevel`）；`Host_Map` 可另计 `map`，不要把两者混为同一路径。
2. `SV_ServerShutdown`（`deactivate`），覆盖Steam通知和整个Metamod/GameDLL调用。
3. `SV_LoadEntities`（`entities`），覆盖 `.ent` 与 BSP 两种分支。
4. `ED_LoadFromFile` 中仅首个 worldspawn 的 `pfnSpawn` 聚合（`worldspawn`）；计入实体阶段，禁止再次相加为总量。

如果确认 worldspawn 占主导，再在 GameDLL 加 `CSOL_PrecacheCharacters` 的清单校验/模型预缓存与 `CSOL_PrecacheGameRules` 的分段timer。保留完整验证、资源顺序及真实模型语义；没有数据前不跳过角色、不替换为任意代理模型，也不缓存未验证的存在结果。

timer日志本身在析构函数读取结束时间后输出，因此外层timer还包含子timer写日志成本；实际总量以最外层为准。后续工具应记录 `observedSeconds` 与 `engineChangelevelSeconds`，另给分阶段，不再把两项之和标作完整serverLoad。此报告不修改生产行为或提出未经IDA证明的CSOL加载实现。
