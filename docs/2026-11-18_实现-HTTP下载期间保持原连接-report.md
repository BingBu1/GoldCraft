## 连接、资源与取消所有权

HTTP 作业持有本次加载门，原 Precache 暂不消费未完成的资源。主线程每秒最多发送一次原有 netchan 的空包；网络协程不访问引擎／VGUI。八路 Asio、重试预算、完整临时文件原子发布与下载进度保持。

全部作业结束后，Tick 把作业交给静态的命令所有者，排入 `gc_download_continue`。原生加载可能以 Host_Error 非局部返回，因此不能在持有 Tick 自动 C++ 对象时直接调用。命令再次核对批次代次和原状态，逐项把已成功发布的实际文件交给原 ProcessFile；失败文件不标记成功。最后重入原缺文件批次，执行剩余 UDP 回退或正常 precache/register/spawn。这里不发 retry，不关闭仍由原生连接拥有的进度页。

显式取消调用完整原取消逻辑。只有原取消中的那一次 Reset 仍对应当前代次且原连接仍为状态 4，才执行真正的原断线；取消回调若建立了新队列，不能断开新队列。新地图、取消、手动断线和退出均退休待执行命令。取消后旧 UI 回调误重连的独立修复及旧反例见 [队列回调修复](2026-11-18_修复-下载队列取消后旧回调误重连-report.md)。

新增热路径仅为主线程代次／状态比较、一次时钟检查及有界保活；不加逐资源资源查询、不增加网络线程、不跳过校验。该改动改善下载生命周期，不宣称完整入图速度已达标。

最终夹具使用八个从未存在的独立 WAV 文件，通过仅改变资源能力字段的 loopback 适配器进入真实原生 v3 HTTP 分支；身份／认证字节未改。HTTP 是服务端真实资源的本地代理，八个响应各延迟七秒。入队后服务端超时临时设 4 秒，验证下载期间保活；HTTP 完成后恢复正常 60 秒供模型载入。最终只有一次 connect 和一次能力适配，八文件均成功，客户端继续原生加载并达到 active 状态 5。真实日志出现 retaining connection、8/8 complete、八次 ProcessFile、continuing on the same connection；不存在测试脚本发送 retry。
