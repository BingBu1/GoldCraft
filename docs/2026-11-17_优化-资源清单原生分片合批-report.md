# 资源清单在原生分片上限内合批

实测换图时，4,057 项清单按 128 项逐批到达，从第 29.54 秒持续到第 42.99 秒。原发送器把每个完整清单消息单独加入可靠分片等待队列。本轮只合并这些完整消息，保留原协议、资源顺序、完整 SHA、代次和一致性检查。实际换图的总耗时与界面响应仍须重新采样，不能用队列数减少推算已实现的秒数收益。

## 原证与修改边界

原生客户端样本为工作区 `analysis/model-read-span-20261117/host-hw.dll`，x86、ImageBase `0x10000000`，SHA-256 `9ba9a2db5e07598fd59afa35507a98c86162e4e15b3835177b78c11842cd2295`。这次使用宿主传输证据，不改变 CSOL 游戏规则，也不声称原版 CSOL 有项目的扩展清单协议。

修改前合同在 `analysis/manifest-transport-20261117/PREEDIT.json`；恢复本轮时重新读取当前源码与样本，额外识别一致性 Hook，先封存 `RESUME-PREEDIT.json` 再编辑。此前其他领域修改的 `sv_main.cpp` 未被覆盖，消息 Hook 和一致性消费者保持原源码。

合并不跨越完整消息，不改变每块 128 项上限，也不放大 UDP 包。每个合并后的未压缩消息仍不超过 `NET_MAX_PAYLOAD`。使用两个固定大小栈缓冲：一个原消息和一个合并载荷；逐块只复制一次，没有逐项新分配、同步磁盘读取、额外网络线程、计时器或跨图缓存。消息字节填充由原位写入器完成，原生分片函数仍负责压缩与排队。

## 自动验证

服务端回归直接使用实际 SDK 类型、真实 Hook 注册表、原位写入函数、一致性写者、BZ2 库与普通分片队列。生成适配器仅包含明确列出的完整函数和位写入存储类型，没有复制源码树。能力握手、致命错误策略和内存分配是明确的夹具边界，不冒充网络实服。

- `build/manifest-transport-sdk-20261117-04/receipt.json`：263,456 项检查、零失败，输入前后稳定。覆盖 v3/v4、空表、1/127/128/129/512/4,057/16,384 项、最长文件名、自定义 MD5、保留字段、完整文件大小和 SHA、一致性尾表，以及两类 Hook 的精确可靠组顺序。
- 旧发送器固定取自 Git `d7b6f094e8d547635e4b297e0be61118a78e5e39` 的真实完整函数，只重命名为测试入口。每例分别执行旧/新发送器，经原生队列压缩、分片、重组并解压后，整体服务消息字节逐字节相同；存在任一 Hook 时连组边界也逐组相同。
- 固定旧发送器反例 `build/manifest-transport-old-20261117-01/receipt.json`：编译/链接成功，准确失败于 `former sender keeps one reliable group per 128 entries`，按预期退出 1。编译、链接或其他失败不算该反例通过。
- 4,057 项典型长度夹具：v3 为 32 → 4 组，v4 为 32 → 6 组；最长名字/全部保留字段的 v4 为 32 → 11 组。16,384 项对应 128 → 22 组或最长情况的 43 组。它们是确定的队列结构结果，不是实际公网或整图性能成绩。
- 当前真实客户端 `parse_resources` 连续消费服务端生成的分组消息，v3/v4 共 138,242 项检查、零失败。核对所有记录、MD5、保留字段、一致性索引、完整大小、SHA、代次，以及只在最终清单完成后启动下载；原有解析/可逆补丁/延迟预缓存等回归也通过。`build/manifest-transport-client-20261117-01/receipt.json` 因未被编译消费的购买菜单源变化正确拒绝整树状态，没有改写此失败；随后按实际 Ninja 依赖、对象、库、EXE、工具和网络输入逐项封存并重新执行，独立 `build/manifest-transport-client-20261117-02/receipt.json` 的 574 项输入稳定，仅证明该客户端组件，不接受整树漂移。

首轮夹具未带入原生 `bf_write_t` 完整定义，编译正确失败；随后实际类型作为窄适配器从 SDK 提取。第二轮缺少未改动的客户端能力边界，链接正确失败；显式补齐夹具准入条件后重跑，没有放宽任何生产检查。首败日志保留。
