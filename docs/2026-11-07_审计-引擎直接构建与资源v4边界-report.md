## 真实调用链

1. `SV_CreateResourceList` 尾部（当前约 5886 行）无条件调用 `GC_ResourceSyncBuild`，失败经 `Host_Error` 拒绝该次地图准备，之后才 `GC_HttpResources`。这段不检查是否有支持 v4 的客户端。
2. `GC_ResourceSyncBuild` 对可下载普通资源生成 SHA-256；文件身份缓存命中时可不读正文，首次、身份变化或 metadata provider 不可用时读取正文。多达 16,384 个缓存条目跨图保留；每图清单、generation 和 ready 状态按生命周期重建。
3. `GC_SendResourceManifest` / `GC_WriteResourceChunk` 按客户端 `gc_precache=3` 且 `gc_resource_sync=1` 决定是否发 v4，v4 附 generation 和 size/SHA。只有这里有按客户端能力的分支。旧客户端仍收到 v3，但并不能免除第 1 步的服务端准备成本。
4. `GC_HttpResources` 将当前清单的完整性条目附给 HTTP Store。HTTP 主线程读取正文时增量计算 SHA，`CloseRead` 和 `Store::finish` 都核对冻结摘要。关闭 HTTP 本身不跳过第 1 步。
5. `GoldCraftPrecache::Reset` 调用 `GC_ResourceSyncReset` 清理每图清单。HTTP refresh 只重新发布现有摘要，不能激活新的文件身份。
6. 客户端 `precache_client.cpp` 已有 v4 解析和暂停/恢复入口，但当前项目搜索 `set_resource_sync(` 只有定义、没有生产调用者。注册能力时 `can_update = client_media_enabled && sync_callbacks.available && sync_callbacks.available()`；尚未接回调时广告 0。这不是完整的资源更新事务。

## 最小启用边界建议（尚未实现）

直接构建根源码前，需要显式选择资源更新是否启用，不能只改清单版本数字或让客户端广告 0。若换图性能候选需保持运行版 v3 行为，至少同时控制：

- 地图资源列表完成后的摘要准备及其专用错误路径。
- `GC_ResourceSyncClient` 的新能力协商。
- 关闭状态下每图清单始终为空，使 HTTP 条目不带 required 摘要、不触发新增正文 hash；reset 仍可正常清空状态。

可用默认 OFF 的明确构建属性形成待完成功能边界。不得用虚假的摘要准备成功或修改原一致性校验掩盖未接通状态。该门若获采用，仍须做开启/关闭与原 v3 发包、HTTP 的联合回归。正式启用还需完成客户端实际事务、模型/字体/渲染消费者失效、取消/退栈/断线恢复和旧资源更新实机验证。

已存在 `tools/Build-ReHLDS.ps1 -Output build/rehlds/Release -MaxJobs 1 -NoPublish` 可以直接编译项目并重建缺失对象；它本身不会隔离上述工作树 WIP，因此不能在边界决定之前当作当前候选的安全一键部署路径。
