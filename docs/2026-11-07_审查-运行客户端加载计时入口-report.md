## 可直接推进的结论

**当前 CSOLSupport 已有 `CSOL_HITCH_TRACE` 计时器，可在下次正常启动前设置独立 CSV 路径，无需先重编客户端。** 运行版含旧诊断源码，而根源码不含相同插桩，不能根据根文件没有计时便断言运行 DLL 没有计时。

以下地址为 E1 CSOLSupport 的首选 VA，映像基址 `0x10000000`；RVA 等于 VA 减基址，不能作为重启后的绝对内存地址。

|---|---|---|

| `csol_hitch::Scope::~Scope` | `0x1000FA20`（`0xFA20`） | QPC 时间转换为微秒，按各 Scope 阈值过滤；FILE 非空且记录数未达 100000 才输出 |

| `SceneFrame` 调用 `fflush` | `0x100234EC`（`0x234EC`） | 有 FILE 才刷新，随后记录 `trace-flush` 耗时并更新刷新时刻 |

PDB 第 411 模块（零基）给出 resources 的实际函数 section/offset；第 413 模块给出 SceneFrame。`llvm-objdump -d --start-address=... --stop-address=...` 的调用目标，分别用 PDB publics 中 `_getenv`、`_fopen`、`_setvbuf`、`_fflush`、`_fclose` 核对。字符串消费者核实了开关与 `wb`，并非仅凭字符串猜测。

审计时该实例 recorder FILE 为 0、rows 为 0，所以当前进程不记录 CSV。开关不是 cvar：应在启动子进程前设置环境，父进程后来更改环境不能打开已初始化的 recorder。目标目录须预先存在，使用新路径避免 `wb` 截断旧证据。

刷新依赖 SceneFrame 继续执行；加载卡住时 CSV 暂不增长并不证明没有采样。恢复后至少等超过两秒的 SceneFrame，并在正常退出后读取最终文件。`trace-flush` 行在 fflush **之后**写入，它本身通常在下一次刷新才落盘。强杀可能丢失末尾缓冲，不能据残缺尾部判定整个加载完成。

已存在历史样本 `build/map-transition-stall-20261106/optimized-live-01/client-trace.csv`，最后写入 2026-11-07 15:06:18。包含 `LoadStudio`、`ReadResource`、`GetAsset-miss`、`ModelSource`、`ModelDecode`、`StudioBounds`、`Materials`、`CommonMaterials`、`LoadImage-miss`、`UploadImage`、`Geometry`、`Geometry-upload`、`DrawModel`、`frame-gap`、`trace-flush`。它跨较长区间，不能冒充下一轮受控跨图样本，也不能把所有列简单相加。

## 测量解释与下一步

P1（callflow，E2/E3）：宿主 `Mod_LoadModel` → CSOL `LoadStudio` → 文件读取/解码/SEQ/owner → 下游宿主及 Renderer；首次显示还会走 `GetAsset` → 材质/图片/几何上传。缓存命中、进图 loader 和首次绘制必须按时间区间区分。

F2（E3，高可信、可直接采样）：主协调下次正常启动前设置 `CSOL_HITCH_TRACE` 为独立 `build/map-transition/client-hitch.csv`。保持同 DLL、同地图序列和正常配置，记录启动/换图时刻及旧文件是否存在，采样完等刷新并正常退出。先按同一换图区间分别统计 inclusive 总时长和最长项；短于阈值的调用缺席不能按零耗时或全部调用计数解释。

F3（E2/E3，高可信、归因边界）：现有 CSV 可先区分资源读取、整体 Studio 加载与首次资产/GL 提交，但 `Exists/FileExists` 没有独立已核 CSV 阶段，SEQ 合并也未独立分项。`LoadStudio - ReadResource` 仍混合解码、SEQ、owner、下游加载/Renderer，不能直接命名为“SEQ 耗时”。GL 上传是 CPU 侧调用耗时，未等待 GPU，不是 GPU 执行时长。

当前 Renderer 源 `gl_model.cpp` 区分 lazy 首次创建与已有 render data 重建；`gl_studio.cpp` 的 header-hash 命中仍重载材质/外部配置并创建异步任务。由于缺运行匹配 PDB，这些只用于后续诊断设计，不作为本次运行瓶颈证明。若 CSV 仍留下大块未知，再闭合 Renderer 身份并对存在性查询、SEQ 和下游缓存单独加测量；不删验证、不换代理模型、不延长超时。

验证层级：身份与诊断控制流已核；生产逻辑修改、编译、部署、实时计时采集及画面验收均未在本子任务进行。共享状态文档更新文本交主协调，避免覆盖并行编辑。

### 时钟可比较性

实际采样工具使用 Python 3.14.3 x64；`time.get_clock_info('monotonic').implementation` 返回 `QueryPerformanceCounter()`。直接调用 Windows QPF 得到 **10000000 Hz**；三次 `monotonic_ns → QPC → monotonic_ns` 夹测，换算的 QPC 纳秒均落在前后两个 monotonic_ns 之间，完整值见小 JSON。

客户端 E3 指令将绝对 QPC/QPF 转换为纳秒再除 1000，未减本进程启动时刻，因此同一机器、同次系统启动中的 CSV 微秒与 Python monotonic 秒可以对齐。本次窗口为 **17598669385.8–17622049026.5 µs**；客户端整数微秒有截断误差，不能据此声称亚微秒边界精度。不是用 Unix 时间直接对齐 QPC。
