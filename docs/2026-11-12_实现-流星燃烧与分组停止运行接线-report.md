## 运行逻辑

新增严格的 `native/csol/scenario/bosses/teddy_meteor.hpp` 只消费已证 Meteor 85B 和
group2/owner0 的 47B stop 形式。其他 TempEmit 继续原消息链，不注册假的 PEmitter 接收器。
实际运行代码在 `native/csol/client/scenario/core/particle_effects.cpp`：Meteor 与出生火花、
黑洞烟雾、滑行使用同一个 128 记录 owner 和普通粒子 owner，不额外分配容量。

每只手的 emitter 为 group2、无限次数、间隔 .01、life .2，附件分别为 0/1。
每个合格发射先经过已证消息戳校验，采对应的 SDK `owner->attachment[index]`；没有模型头判断
或改用实体原点的回退。单次发射严格保留：

1. Float(0,3) 加 packet size，然后 Long(0,2) 选 burn5/6/7。
2. Z、Y、X 三次偏移随机，再逐轴加到该次附件世界位置。
3. 实际工厂分配；失败结束整个 pass，只消费前置四次 Float 与一次 Long。
4. 成功后独立采 PVS-time、born，再消费三次 spread Float 和 mass Float。

`die=FrameSnapshot+.2`，并不重新用 born 加 .2。已经发射的粒子保存世界位置，不再跟随手掌。
Update 继续循环帧、growth、fade、无碰撞运动与实际摄像机消费者；没有复用固定尺寸的 Sliding Tick
或出生火花的有限动画。fade0 为 `250*(1-(now-born)/(die-born))`，保留每步 float32 舍入，
alpha<1 即令 die=now，不能改为只有 alpha<=0 才退役。

stop helper 的四字段写入顺序为 tag、active、remaining、total，其他 record 字段保持。
普通粒子内存和绘制队列不受 stop 影响。`StopTagged` 的 host 重入保护不冒称原游戏存在递归消息处理；
已有 `busy` guard 继续拒绝宿主回调中的递归消息，不扩展未知断线或 ResetHUD 策略。

## 冷资源与宿主适配

原游戏的三精灵随客户端安装，在公共 VidInit 加载；这个宿主的 FastDL 资源可能随后才到达。
因此在第一次接受 Meteor Add、且确实找到空闲 emitter 槽后，冷准备三个 companion 模型，
再执行原 packet burn5 的 Add 加载。HUD 时间缓存仍在这些资源回调之后读取。
Frame/Draw 不做模型加载或缺失模型替换；选中的 companion 缺失时仍按原工厂失败顺序退出。
已有场景重置清除 host 保存的 companion 引用，没有新增原生命周期假设。
