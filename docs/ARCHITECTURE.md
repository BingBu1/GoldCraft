# GoldCraft 的工作原理

GoldCraft 保留真实 Minecraft 模拟，并把 GoldSrc 地图和原生实体接入它。方块规则、物品、背包、生物 AI 和声音仍由 MC 运行时执行。

## 进程与权威

每位玩家运行一组 CS 客户端和 MC 客户端。本地私有桥接把这一组的 CS 输入送到 MC，并把 MC 的网格、纹理、HUD、手部和粒子送回 CS。A/B 使用不同身份、端口与进程记录，每组有独立摄像机和输入队列。

所有玩家连接同一个 ReHLDS 专用服务器及 MC 专用服务器。ReGameDLL 负责 CS 玩家、原生实体、队伍/生命/重生与形态权限；MC 服务器负责方块、物品和生物模拟。两台权威通过独立桥接交换受验证的状态和动作。本地渲染桥接不能自行授予服务器控制权。

| 数据 | 生产方 | 接收与用途 |
|---|---|---|
| 地图 BSP、clip hull、动态原生实体 | ReHLDS/ReGameDLL | MC 世界碰撞、攀爬、路径支持和交互 |
| MC 玩家预测位置 | MC 客户端/服务器 | 服务器验证，CS 摄像机插值 |
| 方块/生物/粒子网格与纹理 | MC 客户端实际渲染器 | MetaHook/Renderer 的深度、材质和阴影通道 |
| MC 方块/实体代理 | MC 专用服务器 | 原生移动碰撞、子弹/刀/投射物命中 |
| 伤害、治疗、攻击者身份 | 相应权威 | 对端验证，避免重复扣血并保留正常 AI 仇恨 |
| 菜单像素和输入事件 | MC 菜单与 CS 输入 | 原始分辨率 HUD，带菜单代次的输入投递 |

## 协议和坐标

当前源码的固定宽度协议为 GCF1/version 29，定义在 `native/include/goldcraft/wire.hpp` 和 `neoforge/src/main/java/dev/goldcraft/bridge/Wire.java`。传输不包含跨进程指针，允许 Java x64 与 GoldSrc x86 通信。角色、私有配对凭据、连接代次、玩家重生代次和地图会话共同限制旧包和错误配对；序列号、长度与数值范围在边界验证。

Version 28 的 `INPUT` 保持 48 字节布局，原 `enabled` 字段改为 flags：bit 0 表示输入窗口有效，bit 1 表示 pitch/yaw 是本帧相对角差（度）；未知位拒绝。Minecraft 控制时宿主采集相对角差并恢复真实 MC 相机角，菜单／失焦时角差为零；原生 CS 保留绝对角和原生移动。客户端只累加有效相对帧，交给 Epic 原版 `turnCamera`，未消费时走 vanilla 转向。绝对帧、身份变更、断线和不可操作 tick 清除未消费角差；MC 初始朝向沿用服务器传送。协议版本门禁拒绝与旧版混用。

本机链路使用非阻塞 TCP 与 TCP_NODELAY；队列有界，尚未采用共享内存。type64 传递有序后处理计划，type65 分块传递大型纹理，type66 原子提交同一 epoch/revision 的实体底图、附魔／气泡和头像身份。接收端完成校验、纹理就绪检查及分配后一起替换，避免底图和附魔来自不同帧。共享内存大帧通道已排队；需先测队列等待、复制、编解码与 GPU 上传开销，保留已认证控制链路、实例隔离和服务器权威。

地图挖掘使用消息 56/57/58 分别传递 HLDS 政策、Minecraft 服务端请求和原生处理结果。客户端只发送挖掘按键意图；消息 62/63 先按相同权限核验读取真实原生材质，不造成伤害。MC 服务端调用 NeoForge 工具、破坏速度和采集检查 API 累积进度，再通过 57 请求伤害；HLDS 重新检查配对、形态、代次、频率、距离与真实地图射线，最后执行实体原生伤害回调。`mc_map_mining` 的政策会同步和补发；整图几何的视觉／碰撞修改仍需接入，详见[地图挖掘](WORLD_CARVING.md)。

坐标变换在协议实现中统一：每个 MC 方块对应 32 GoldSrc 单位，MC 的水平 Z 对应 GoldSrc 的反向 Y，MC 高度 Y 转换为 GoldSrc Z；MC 高度基准为 64。玩家脚部、原生角色中心与相机眼高分别处理，避免死亡/重生后人物落在地图下。

## 碰撞、原生实体与生物

静态 BSP 可见面不足以表达空气墙。MC 玩家路径结合 GoldSrc 站立/蹲伏 clip hull，生物的支撑和路径查询读取主世界及动态障碍；梯子保留原生体积与行为。门、人质、按钮、触发器和移动实体还需要实际 Touch、Use、伤害和生命周期适配。完整支持范围由实际测试决定，导出碰撞盒仅覆盖其中一部分。

CS 形态也保留 MC 世界交互。ReGameDLL 中的方块和实体代理参与原生运动与武器 trace；命中再交给 MC 权威处理。原生玩家的 MC 代理保留可识别的攻击者身份，使狼的反击和敌对生物主动寻敌沿原版 AI 路径执行。共享生命记录处理确认、拒绝、并发变化与重生。

MC 移动权限有效时，原生玩家镜像的下落速度不能再次触发 CS 坠落伤害。ReGameDLL 根据已认证服务端连接和有效移动状态，把坠落计算交给 Minecraft：创造免伤、生存扣血最终通过共享生命路径提交。退出 MC 形态时清除原生累计下落速度，普通 CS 形态继续使用自身伤害规则。

## 绘制和输入

Renderer 是通过 MetaHook 接入的插件。它接管客户端 `R_RenderView` 和 `R_GLStudioDrawPoints`，由自己的 `R_RenderScene` 调用地图与实体绘制；启用它时并不是先完整执行原版场景绘制再叠加效果。这里的 BSP 合批、参数流及模型提交计划属于替代渲染管线的架构改造，不能表述为已经重构闭源 `hw.dll` 的主循环、可见实体生成、网络或预测。ReHLDS 是专服参考，不是客户端引擎替代品。

最近一次有效 32 灯固定视角样本中，帧间隔平均约 15.63 ms，渲染区间约 12.12 ms，其中阴影约 9.28 ms；相邻渲染区间之间约 3.51 ms 尚未归因。这些是宿主经过时间，渲染区间也包含客户端回调和驱动等待，不能把差值全部记为引擎 CPU。没有新实机数据前，仍不宣称达到 200 FPS。

`r_studio_shadow_plan`（默认 0，需深度执行路径启用）为模型子网格保存可复用的阴影提交计划。每次真实模型回调之后重新判断当前视图和实体状态；原始纹理、网格描述和皮肤表以字节快照检验，能识别同地址材质变更。资源重载清空计划，每个子模型最多保存八种皮肤。普通不透明子模型复用合并索引范围，混合或特殊材质整项回到原有交错绘制路径，避免跳过材质副作用；逐灯回调、裁剪、跟随父模型和动画均保留。复用仍需元数据比较，不宣称扫描成本为零。实际 GL 分层深度／模板／退出状态和变更回归通过，尚无实机收益验收。

参数流和提交计划提供逐帧开关与上传、复用、失效、回退计数。自动光源工具分别支持 `--draw-parameter-stream-modes` 与 `--shadow-plan-modes`；后者要求两侧都已启用深度执行路径，拒绝开关混合、缺失计数或不同前台视角。原 cvar 与测试方块记录在恢复清单，退出恢复；隐藏 GL 正确性测试不计为 FPS 证据。

MetaHookSv 接入客户端回调，Renderer_AVX2 提供 OpenGL 场景通道。GoldCraft 使用三角形/VAO/VBO 和着色器，在 Renderer 的实际深度与阴影流程中绘制 MC 几何。实体按渲染帧插值；动画纹理采用局部更新。手部、持物和 HUD 从 MC 自己的渲染流程导出。

GL 优化优先使用绘制阶段以外的准备工作、不可变 GPU 资源、空间裁剪和兼容状态批次，减少逐帧分配、上传和同步查询。保持精确浮点与画面／碰撞一致性；实机性能对比固定观察者位置和朝向，独立微测试不等同于游戏帧率。

BSP 主绘制在可见叶几何准备阶段生成不可变的跨材质提交范围，按原顺序合并最多六条连续纹理链。支持 `GL_ARB_shader_draw_parameters` 时，完整世界着色器通过 `gl_DrawIDARB` 选择各子绘制的漫反射纹理；纹理单位 9–14 与现有材质、光照贴图绑定分开，支持 multi-bind 时一次绑定整组。间接命令的几何、实例起点、材质缩放及光照样式保持不变，不重采样或缩小贴图。挖掘内壁与普通光照贴图在批次边界分开；动画、特殊材质、水面、portal、多视图和阴影继续使用各自原路径。`r_world_material_batch` 可关闭新提交路径用于同视角对比，缺少扩展时自动回退。

该阶段减少主场景的材质状态切换和绘制提交；每个点光仍重新进入场景绘制，场景收集与多视图队列复用尚未改造。诊断记录实际材质链数、提交数和合批数；真实驱动回归直接执行生产提交函数及完整世界着色器，比较颜色、深度、模板和命令数量。它们验证正确性和提交合并，游戏帧率仍须在单 B、24 Bot 的真实场景验收。

不透明人物阴影可把同一模型中连续、材质与模板状态相容的三角形范围合成一次索引绘制，复用已有 EBO，不在收集时分配或上传几何。每次调用重新检查当前皮肤、材质和视图；特殊材质、透明／镂空、范围间隙及不相容状态保留逐网格路径。现有 `r_studio_shadow_depth_executor` 同时控制单网格深度路径与这一合批，默认关闭。真实 GL 回归验证分层深度、模板、退出状态和实际提交数；关闭／开启的游戏对比不能把整个差值单独归因于合批。这一步尚未实现跨光源场景队列复用，也不改变动画或模型回调。

人物及 BSP／brush 的完整绘制参数现在共用有界的持久映射参数流。旧路径每次覆盖同一个 UBO；新路径从三个固定 256 KiB 页中取得对齐切片，CPU 写入后按范围绑定，切片保持整帧不可变。外层帧开始统一开放写入，所有视图、阴影和结束回调执行后插入 GPU fence；下一帧每页最多轮询一次且超时为零。页满、GPU 尚未消费或设备不支持时，使用独立的旧可变 UBO，不等待或覆盖在途页。资源随 Renderer 上下文初始化／释放；相机、部分更新缓冲及骨骼算法保持原有生命周期。

`r_draw_parameter_stream` 默认 `0`，用于独立比较这一提交路径；`r_draw_parameter_status` 显示上传、字节和回退统计。新回归执行生产上传函数，在两个不共享的 WGL 上下文比较连续帧的实际颜色／深度，覆盖双绑定、跨页、满页、重建及可选功能缺失；确定性忙页／同步失败注入与实际驱动画面检查分别标识。本轮 5 组回归通过，新测试有 43,026 次实际绘制和 2,850,816 组像素／深度比较；这不证明游戏帧率提升，尚未实机启用验收。

模型提交计划已经实现并通过上述正确性回归；跨光源的整个场景队列仍未复用。不能录制第一盏灯后直接跳过其他灯的回调；皮肤、材质重载及特殊效果可能在其间改变。最近有效 32 灯同视角样本约 63.99 FPS，阴影 CPU 约 9.28 ms；200 FPS 和稳定约 100 FPS 仍未达到。

贴花几何统一准备时，先验证引擎池中的表面指针属于当前实体模型及子模型范围，再读取 polygon 和材质。换图或 GL 资源尚未就绪时清除对应绘制缓存与 VBO 标记，保留引擎槽位；资源恢复后重新准备，避免访问已失效的表面或永久丢失贴花。生产路径回归覆盖缺失资源、异址／未对齐／越界指针、已缓存资源失效及恢复后的实际像素。

大型粒子纹理的分块接收使用单块、最多 64 MiB 的可复用 CPU 暂存。首次申请的内存不预先清零，只有所有连续分块校验通过并写满后才允许读取；完整 GPU 上传成功后发布新纹理，并保留暂存供下一张图使用。增长时先释放旧暂存，避免同时持有两张大图；换图、生命代次变化、断连及错误路径释放暂存。原有 epoch/generation/life/revision 和 128 MiB 已发布纹理预算保持。针对性测试验证最大尺寸重传、缩小再放大、取消、乱序及分配失败恢复，并在禁止分配时完成热传输；这些是正确性与分配开销证据，不是实机 FPS 验收。

客户端诊断分别记录暂存实际容量、分配/复用次数，以及首片接收、续片、GPU 上传、发布和上传失败清理的耗时。计时采用宿主经过时间，可能包含驱动等待；它们嵌套在纹理消息总耗时内，不能相加，也不等于 GPU 执行时间。完整图片仍在接收完毕后上传；进一步拆分 GPU 上传需要依据真实分阶段样本决定。

Renderer 的前向点光使用 16 字节数量 UBO 和按实际数量增长的只读 SSBO，每条记录为两个 vec4（32 字节）。世界和人物着色器共用同一布局，消除旧 256 项栈数组的越界风险；不截断超出 256 的可见点光。设备容量在资源初始化时查询，CPU 镜像和 GPU 容量复用，逐项比较内容，仅在变化时上传有效记录。容量不足先受控报错，不发布截断的光源表。

阴影深度视图不收集点光表，只将 GPU 数量清零；普通前向、水面和 portal 视图恢复数量与绑定。延迟光照继续使用原有光体积路径。数量 UBO 与记录 SSBO 都使用各自命名空间的 binding 2，每次恢复绑定，不假设跨回调状态保持。相关测试分别验证大于 256 的光源贡献、硬件容量边界、相同记录无重复上传和视图切换；独立 GL 测试不代表完整游戏 FPS。

Studio 人物绘制把原来每次上传的 6368 字节 UBO 拆成 224 字节绘制参数和 6144 字节骨骼矩阵。光照、颜色、观察位置和骨骼裁剪掩码仍逐次更新；同一渲染帧中，完整矩阵经哈希及字节比较确认相同后，复用已上传的骨骼缓冲。缓存最多保留 256 套姿态，超出时使用独立缓冲完整上传；这一容量不限制实体或姿态数量，也不丢弃绘制。下一帧清除内容索引并复用存储，换图和关闭释放资源。

骨骼使用 UBO binding 4，与材质 SSBO binding 4 是不同命名空间，每次绘制都会重新绑定。动画、骨骼合并、物理和公开 Studio 回调照常执行，缓存不依赖“同一实体等于同一姿态”的假设。`r_studio_bone_palette_cache` 可关闭内容复用以作同视角对照，诊断记录实际上传、复用、上传字节和容量回退次数。该开关只控制复用；关闭时仍使用配套的分离 UBO 布局，Renderer DLL 和着色器必须一起更新。

骨骼合并诊断分别统计缓存命中、未命中和绕过缓存，并将缓存查询／矩阵复制与原生合并调用分阶段计时；原来的 `boneCacheHits` 仅统计 SetupBones，不能用来推断 MergeBones 的命中率。新增计时沿用有界、按需启用的 CPU 采样，不增加 GPU 查询或改变骨骼计算。汇总检查各类次数与实际调用数一致；子阶段嵌套在合并总时间内，不能相加作为帧耗时，也不能把原生合并时间全部归因于骨骼名称比较。

CPU 骨骼缓存使用预分配的 2048 个哈希桶和 1024 个姿态索引，替代每帧清空后重建节点的 `unordered_map`。索引保存原始完整姿态键，哈希相同仍须逐字段相等，保留正负零相等和最后一次保存覆盖矩阵的行为。每帧只重置桶和计数，复用索引与矩阵存储，不逐节点申请或释放内存；满额仍可更新已有姿态，新姿态走原有未缓存计算，不丢弃人物。此缓存与 GPU 骨骼缓冲复用独立，不改变动画或物理回调是否执行。回归测试以完整矩阵、碰撞链、跨帧线性参考和堆分配计数验证这些行为，实机收益仍须固定视角测量。

GoldCraft 的 GL 状态快照内置于 Pass，按不透明／透明／HUD 实际修改范围保存和恢复；选框与裂痕才读取线宽和偏移参数。着色器位置和设备常量按上下文缓存，纹理参数只在新纹理创建时设置。相同纹理／发光／深度状态在单个独占 Pass 内去重；外部插件拥有的状态每次入口重新读取，不跨回调假设。上下文切换或关闭会清空相关缓存。

MetaHook 按插件清单的逆序调用 LoadClient。清单中 Renderer 位于 GoldCraft 前面，使 Renderer 包裹最终的 GoldCraft 摄像机结果；不能随意交换顺序。每个 MC 发光源请求阴影，静态 BSP 遮挡可缓存，动态实体与 MC 几何按帧更新；新版室内效果仍需实测。

输入拥有者由服务器决定。MC 形态转发动作并抑制原生武器展示；CS 形态恢复原生武器、HUD 和控制。背包输入只接受当前显示菜单的代次。NeoForge 对容器按键 API 有补丁，迁移版针对 `isActiveAndMatches` 适配，正常 MC 窗口仍保留其自身绑定。

形态菜单通过 AMXX 的 ShowMenu/menuselect 在服务器执行选择；MC 形态由合成器补绘菜单。被动 Minecraft 聊天使用独立 HUD 标志，在原生 CS HUD 之后叠加，不触发手部模式。MC 游戏中 `/` 转发到原版命令键；已有菜单里的斜杠继续作为文字输入。

形态菜单在 CS 和 MC 展示中都由同一路径处理选择，同时关闭原生菜单与镜像，只发送一次 `menuselect`。菜单绑定按下后锁存至释放，按键重复不再开关菜单；MC 界面打开时保留文字输入，即使字母在 CS 中绑定为形态菜单。普通 CS 的其他 AMXX 菜单继续沿用原生处理。

收到服务器确认的 MC 形态／新生命后，客户端仅在玩家存活且本地连接有效时保留最长 500 ms 的展示交接期，等待当前生命的 HUD；此期间隐藏 CS 武器与 HUD，击杀提示和菜单仍可绘制。交接不复用旧生命的姿态或 HUD、不授予控制权；死亡、断链或超时恢复原有回退。MC 就绪状态变化立即申请服务器控制，未获确认时每 50 ms 重试，确认后的租约仍每 400 ms 续期。

粒子贴图属于连接、地图和资源代次，同一代次的贴图及未完成分片不因玩家重生而清空。每次传输仍保持最初的生命字段一致；粒子、实体和后处理展示仍严格验证当前生命。该调整需要 DLL 与 JAR 配套部署，旧 DLL 会拒绝跨重生的分片。首次加载与资源重载仍须完整传输，不能据此声称所有特效延迟均已消除。

NightFall 3.4.0 的一个服务端动画回调以非短路 OR 读取 CLIENT 配置。兼容 Mixin 只将该处读取改为专服默认值，客户端继续读取用户选项，保留动画事件、声音和伤害逻辑。实际生产类的 Sponge 变换与独立处理器回归由 `tools/Test-NightfallConfig.py` 验证；实服技能仍需单独验收。

同版本 Yamato 的地面特效回调无下界地逐层读取方块，在没有床岩的宿主维度会永久循环。两个读取点通过 `NightfallGroundProbe` 保留真实 MC 方块、识别当前宿主碰撞形状，并在超出世界高度时结束。返回的石头／床岩状态只供这次探针使用，不写世界、不替换全局方块读取，也不取消后续声音或技能事件。`tools/Test-NightfallGround.py` 检查实际 Sponge 变换并执行抽取的原始／修复循环；宿主形状测试使用 CPU 适配器，不能替代实机特效验证。

该探针在世界上界之外也立即结束，不保留原实现从高空继续向下搜索的行为；宿主薄面、斜坡及负 Y 落点精度尚待实机验证。后续 Epic Fight 地面碎裂函数仍读取真实方块，宿主地板对应 MC 空气时可能跳过碎裂视觉。此修复解决已定位的无界循环，不代表所有地形特效适配完成。

## 地图会话与版本边界

宿主地图修改已有版本化记录、碰撞、Renderer 统一提交及 PVS/PAS 适配，独立测试通过；生产挖掘尚未接通几何写入，动态 BSP 和实际客户端验收仍待完成。接口和限制见[地图挖掘说明](WORLD_CARVING.md)。

地图与会话代次共同确定 MC 宿主维度。换图或 ReHLDS 重启产生新会话并清除建筑；断线重连、区块卸载及资源重载不能被误判成新地图。

ReHLDS 是服务器引擎参考，不是闭源客户端 `hw.dll`。客户端 Hook 按实际二进制身份和 MetaHook `ResolveGameSymbol` 合同匹配模块相对地址；[GoldSrc_VibeSignatures](https://github.com/HLND2T/GoldSrc_VibeSignatures) 提供参考目录，不允许跨版本照搬偏移。全部上游版本记录在 `sources.lock.json`。

本机渲染大帧支持认证后协商的 64 MiB 共享内存环，控制／服务器链继续 TCP，激活前失败可回退。协议 27 两端需配套更新；队列、重连和测量边界见 [共享内存](SHARED_MEMORY.md)。

协议29增加 NightFall 黑白冲击 kind7：有界30个float包含实际uniform、主目标清色RGBA与blit颜色乘数RGBA；旧kind1–6仍为8个float。kind7不拥有遮罩批次，保留有序插入位置；旧端通过协议协商拒绝不匹配版本，须配套更新DLL/JAR。CS侧复用私有RGBA8目标，保留原始双pass颜色量化和alpha混合，不读取场景到CPU。
