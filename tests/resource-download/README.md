# Resource downloader integration tests

`run.py` freezes the actual client downloader and protocol header, builds the x86 C++20 module, then runs it against a controlled loopback HTTP server. Python-generated bytes and `hashlib.sha256` supply the independent expected body and manifest digest. No engine or game process is needed.

Run from the project root:

```powershell
python -X utf8 -B tests/resource-download/run.py --compiler "$env:GOLDCRAFT_LLVM_ROOT/bin/clang-cl.exe" --output build/resource-sync-download-check
```

Use a fresh output directory and the configured Clang/Windows developer shell. An exported toolchain environment can optionally be supplied with `--environment`; personal paths are not embedded in the test. Compilation is sequential. The test writes only its build directory and starts a temporary loopback server on an OS-assigned port.

Cases cover a changed body with unchanged length, old body and old digest rejection, truncated and wrong lengths, HTTP 200 with incorrect content, 404, forbidden redirects, retry after two 503 responses, cancellation and later reuse of the worker, rejection of resubmitting a completed Job, queued cancellation, and asynchronous request callbacks during repeated shutdown/destruction. HTTP request logs prove retry counts and absence of redirect follow-up requests.

The tests exercise WinHTTP and BCrypt directly. They do not verify engine resource mounting, actual game UI, production HTTP endpoints, TLS certificate cases, pathological DNS behavior, sanitizer instrumentation or simultaneous calls to `Shutdown` from multiple threads.
