# 角色模型加载校验计时

`run_safety_bench.py` 复用同目录 `run.py` 已生成的 x86 / O3 / ThinLTO / AVX2 编译参数，直接包含真实 ReHLDS SDK 与项目头文件。仅在 `build/engine-studio-safety-bench` 写编译产物、输入身份和计时结果；不写生产模型，不复制源码树。

准备（不编译、不执行）：

```powershell
python tests/engine-studio-storage/run_safety_bench.py --prepare-only
```

在统一安排的编译窗口执行同一命令并去掉 `--prepare-only`。默认从沙盒专服实际角色目录读取唯一 alias，逐个加载并释放；不会同时保留全人物模型。

## 测量范围与纠正

2026-11-07 准备阶段实际读取目录：151 个角色条目对应 150 个唯一 alias，全部没有 `SequenceSafety` 标签，也没有相邻的首个 SEQ 文件。先前“已打包角色会在三处重复扫描 RLE”的判断不适用于当前角色文件，已撤回。三次安全扫描只是 **tagged 输入的条件路径**，不能作为现服事实。

夹具保留原始输入，分别测量实际 `ReadSequenceSafety`、`PreparedSequenceModel::Read`、`PlanStudioStorage`。前两处对于本批未标记模型通常很快，最后一处仍会逐动作扫描 RLE。出现邻接 SEQ 时夹具明确拒绝，需要另用完整加载入口，不通过人为补标签制造热点。

每个模型默认重复三轮；“三轮”是重复计时次数，并非断言每次角色加载都完整扫描三次。结果包含模型/源码 SHA-256、实际 SDK include 身份、x86 PE 检查、输入前后未变检查。

这是离线缓冲区成本：哈希读取会预热系统文件缓存，计时不包含真实引擎 hook、缓存淘汰、世界初始化、HTTP 下载或客户端重新入服。不能替代父任务的专服分段计时或宣称换图总时长。

## 局部候选

仅为 bench 提取当前 `Animation` 与 `PlanStudioStorage` 两个函数，替换前者私有 `roles` 标记循环为 `memchr(3-role)` 冲突查询加 `memset(role)`。`roles` 仅能为 0、1、2；失败后函数立即返回且不对外发布此临时数组，所以失败前已写多少字节没有可观察差异。奇地址、同角色共享和头/样本冲突仍按字节检查。候选未接入任何生产路径。

准备了 12 个明确 RLE 边界，包括有效/短表、普通/奇偏移/共享轨道、表内或越界偏移、零 valid、total 不足、缺少终点保留字节、帧数耗尽失败、头与样本重叠；另逐个比较实际人物模型的缓存前缀资格和字节数。原/候选规划测量交替执行，减少固定次序偏差。

## 2026-11-07 实测结果

统一窗口内完成 x86 编译、链接和执行；总计 15.24 秒，12 个边界通过，150 个实际模型的 450 组原/候选结果一致，实际消费 596 个 include，源与模型前后 SHA-256 未变。模型总计 1,229,174,960 字节。详细输入身份及结果在 `build/engine-studio-safety-bench/{plan,result}.json`。

| 重复轮次 | 原缓存规划 | memchr/memset 候选 | 候选变化 |
| --- | ---: | ---: | ---: |
| 1 | 0.683929 秒 | 0.788869 秒 | 慢 15.3% |
| 2 | 0.669928 秒 | 0.759449 秒 | 慢 13.4% |
| 3 | 0.671099 秒 | 0.756538 秒 | 慢 12.7% |

全表 `ReadSequenceSafety` 合计每轮 19–29 微秒，owner prepare 为 9.5–21.6 微秒，进一步证实这批角色不是三遍完整 RLE 扫描。缓冲区文件读取为 2.329945 秒，此项有事先哈希造成的系统缓存影响，不能当作冷盘或实机读取时间。

**拒绝采用此候选。** 返回一致并不等于性能更好；本轮没有任何生产行为改动。父任务同轮实机 profile 显示 CRC 为更大的热点，应先针对该路径取证和测量。候选仅作为已否决方案的可复现证据保留，不进入生产构建。
