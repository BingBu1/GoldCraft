`ResumableWeaponAction` is a narrow typed mixin queried by the generic kick controller. A nonzero generation token identifies one custom suspension. Each Glock stores one bounded record with current owner/weapon lease, native spawn identity and presentation sequence; it stores no old ammunition. The controller must begin suspension before replacing the viewmodel, resume only the same currently selected item/life, and cancel when its action retires. Glock independently rejects changed owner/weapon/backend/model/spawn identity. A consumed token cannot resume twice.

While suspended, the normal input methods and ItemPostFrame admit no new weapon input. `AdvanceOwnerFrame` may continue spread recovery. Existing weapon Think callbacks remain active; they may damage or complete an already started attachment at their proved schedule. Their view/aim events are deferred and their `MirrorTimers` cannot unlock the kicking player. This is the explicit custom concurrency policy, not a claim that the player lock suppresses entity Think. Holster, invalidation or cancellation clears old callbacks. No callback or old weapon is resurrected after a switch or life change.

At completion, current native ammunition is read. An elapsed reload is committed once through the real arithmetic/observer; an unfinished reload retains its deadline and loading state. The current body, aim and last real sequence are republished, models restored, and existing absolute weapon timers mirrored without a new draw/attack cooldown. The caller releases its own lock only after the adapter returns.

Presentation boundary: the current server effect consumer calls `SendWeaponAnim(sequence)` and has no fractional animation-phase transport. Resume therefore restores the current action's correct sequence, with an elapsed finished reload using the matching current loaded/empty idle. This does not establish exact visual phase continuation; extending the authenticated client transport is a separate parent-owned integration. No arbitrary animation deadline is invented.

Verification must use the actual Glock class and actual SDK owner/edict/backend lifetimes, current reload elapsed/unelapsed, aim, attack, native ammo mutation during suspension, original timers, callback progression/cancellation and duplicate/reentrant resume. Compilation, SDK checks, deployment, gameplay and CPU/frame-time measurements remain separate claims. Existing temporary rejection-policy fixtures are frozen historical evidence and are not new emergency acceptance.
