# Emergency kick: read-only action-resume findings

This note follows the later user request: kick during any weapon action, noon included, stamina-authoritative, no concurrent duplicate. It does not prescribe production edits or claim that the earlier timer-gate candidate satisfies this new behavior.

`human_kick.cpp::Finish` currently releases only its foot-viewmodel lock, then calls the same selected `CBasePlayerItem::Deploy`. That matches the earlier original kick lifecycle but is insufficient for the newly authorized interruption contract. `GlockWeapon::Deploy` sets `selected_=true`, clears `action_.action` and `action_.aiming`, zeroes spread and resets its recovery deadline, and finally sets `ownerAttack/primary/secondary/idle=now+drawDuration`. It also emits DeployPrelude/DeployReset/inventory/sleeve/body/animation effects. Calling it after a kick can restart draw, erase a pending weapon action and extend/reset the old attack or reload clocks. P345's source has the same absolute-clock/deploy pattern but is not in the selected production object set.

The existing `goldcraft::inventory::RestorableWeapon` API is an inventory transaction rollback, not a presentation resume API. Glock `SaveInventorySnapshot` stores its whole action/spread/transitions, absolute timers, private think pointer/deadline, selected state, clip/reload/fireOnEmpty, wear and strict owner/weapon/model/spawn/context identity. `RestoreInventorySnapshot` writes them back and republishes aim. It deliberately rejects mismatched current ownership/life. Replaying a snapshot captured **before** kick would roll back any legitimate inventory/action/think progress that happened during the kick; capturing at kick end and restoring after Deploy would avoid that old-clip rollback but would still run observable Deploy effects and transient state changes, including callback reentry. Neither is automatically correct.

Useful actual consumers for a new narrow weapon resume API:

- `GlockWeapon::Current` authenticates the current selected owner, edict serials, model identity and backend generation around callbacks. A resume token must also carry kick-action generation and native life, and reject weapon switch/death/recycle.
- `GlockWeapon::ReadAmmo` reads the **current** native clip and owner reserve. The end-of-kick path should preserve this current state, not restore an old clip or reserve from kick start.
- `CommitMagazineReload` and the real `GlockWeapon::ReloadCommitted` observer commit at `now >= ownerAttack` exactly once, with `min(capacity-currentClip,currentReserve)`. They publish actual inventory before clearing loading, with callback identity checks. Resume must retain the original absolute reload deadline when unfinished, and may use this same current-state single-commit path when elapsed. It must not refill early or commit once in resume and again on the next weapon frame.
- `PublishOwnerAim` republishes the current aim state without starting an aim transition or resetting its deadline. This is the appropriate model for narrow presentation restoration; it still validates the selected lease and may fail/cancel.
- `PlayerAnimationAdapter::Apply` chooses prepared owner/model action sequences and preserves native movement/death/flinch ownership. It can restart a requested player sequence, so the resume path must choose the current intended action and elapsed pose, not blindly request Fire/Reload again.

Current native frame control: `CBasePlayer::ItemPostFrame` returns while the player nextAttack countdown is positive, so the kick's million-second lock prevents ordinary Glock `ItemPostFrame` from running. `GlockWeapon::AdvanceOwnerFrame` only updates spread. Absolute weapon clocks continue to elapse because the native countdown loop skips items with `UseDecrement()==FALSE`. Weapon entity `NextThink` callbacks are independent: delayed melee, taclight or attachment callbacks can still execute. Inserting kick during those actions requires explicit cancellation/consumption/resume handling, not assuming the player lock stops every callback. The typed owner path currently reports freeActivity, so it also needs deliberate action arbitration rather than a guessed CoF field.

The narrow API should separate **presentation restore** from **weapon action reset**. Capture only the active weapon/life/action identity and the owned presentation lease at kick start; read current action/ammo/timers at the actual resume point. Preserve absolute deadlines and already-consumed events. After each backend/animation/message/reload callback, verify owner, life, active item and action version again. Native countdown weapons require the same preservation principle in their timer domain. No inventory rewind, forced successful Deploy, synthetic ammo grant, unbounded queued delayed actions or repeated reload animation should substitute for that contract.

This is source analysis only. Required future tests are attack/reload/aim/weapon-melee/attachment interruption, elapsed versus unelapsed reload, ammo changes during kick, callback weapon switch/death/recycle, repeated kick requests and one-time resume. The current SDK differential does not execute these new interruption scenarios.
